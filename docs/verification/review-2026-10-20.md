## Reliability findings at the reviewed baseline

### P2 — Failed watcher updates are not retried after recovery

Location: [watcher.py, lines 85–96](../../app/watcher.py#L85), with failure handling in
[okf_loader.py, lines 228–245](../../app/okf_loader.py#L228).

The watcher updates its remembered modification time before ingestion succeeds.
`ingest_managed_file` catches extraction/model/database failures and returns
`False`; the watcher cannot distinguish a failed update from an unchanged file.
If the dependency recovers without another file edit, later polls do not retry.
An older indexed version can remain searchable indefinitely. A restart rescans
files through MCP startup, and an explicit `reload_knowledge` also retries them.

Reproduction used real SQLite, native parsing and the existing test embedding
fixture, with deterministic watcher polls:

1. Index a policy containing “thirty days”.
2. Change it to “sixty days” and make embedding generation raise a temporary error.
3. Restore the embedding fixture without touching the file.
4. Across six polls, observe one ingestion attempt and the original indexed text.
5. Explicitly reload the directory; the replacement content is indexed successfully.

Recommended fix: give ingestion an explicit unchanged/succeeded/failed outcome and
track bounded retries with backoff. Record the acknowledged file version only on
success or confirmed unchanged content. Add coverage for dependency recovery and
files that change again while extraction is running. Avoid tight retries of
permanently unsupported files.

Current workaround: inspect `get_knowledge_ingestion_status`, resolve the reported
failure, and invoke `reload_knowledge`. Browser queue jobs have separate, explicit
retry controls.

### P2 — Deleting a managed knowledge file leaves searchable content behind

Location: [okf_loader.py, lines 186–203](../../app/okf_loader.py#L186) and the
[watcher scan](../../app/watcher.py#L70).

Directory scans process files that exist but do not reconcile missing files with
the registry. Deletion followed by a successful reload leaves both registry and
search rows intact. Renames can therefore leave an obsolete old identity alongside
the newly indexed document. This limitation was already documented in the
[search guide](../search-upgrades.md); it is now visible in README troubleshooting.

Reproduction: index a document, delete its original, reload the directory, then
query the registry and FTS index. Both retain the document and its searchable text.
The reproduction used real native parsing and SQLite with fixture embeddings.

Recommended fix: define an explicit retention/deletion policy and distinguish
missing originals from deliberately retained snapshots. A synchronization mode
should reconcile only documents owned by that managed root, remove associated
vectors/topics/navigation transactionally, and invalidate search caches. Never
prune after an incomplete/failed scan or remove independently imported snapshots.
Test deletion, rename, unavailable roots and independent source-library imports.

Current limitation: `reload_knowledge` alone does not remove these rows. Verify the
source and regard results as indexed snapshots. Source-library removal is a separate
operation; it does not establish deletion handling for the `knowledge/` directory.

## Resolution follow-up

The two baseline findings above are fixed in the follow-up implementation:

- Managed ingestion now distinguishes indexed, unchanged and failed outcomes. The
  watcher acknowledges only successful/unchanged versions and retries failures
  with exponential backoff capped at 60 seconds. New edits bypass an older
  version's retry delay. Startup rechecks files so a failed startup import is not
  silently acknowledged. The initial checksum scan does not sleep per document.
- Completed directory scans reconcile missing managed sources. Registry records,
  vector/keyword rows, topic memberships, navigation, extraction details and
  related failure diagnostics are removed transactionally. Search caches are
  invalidated after commit. Renames remove the old managed identity.
- Missing roots, incomplete walks, roots replaced during reconciliation, and
  reappeared files preserve indexed content. Namespaced imports and documents
  owned by another root are preserved. Originals are never deleted by cleanup.
- GitHub's deprecated checkout/setup-python actions are updated to their official
  v7 releases. Python 3.11/3.12 and Linux/Windows coverage is retained.

[Freshness regressions](../../tests/test_knowledge_freshness.py) cover retry after
startup failure, backoff including the 60-second cap, new edits during backoff and
embedding, deletion/rename, all related index tables, cached search results,
independent imports, unavailable/replaced roots, partial scans, transactional
rollback and diagnostics for deleted failed imports.

Local follow-up evidence is retained in `scratch/freshness-fix/` (gitignored), with
`verify.py` recording the exact final-suite, protocol and live-watcher commands and
environment. This uses the same Python/Mojo environment as the original review.
The live check uses an actual watcher thread, real MiniLM embeddings and Mojo
search, with one controlled model-access failure followed by recovery without
editing the file again. It then deletes the source and checks search/navigation
removal without a manual reload. HTTP intake and Python stdio MCP acceptance were
also checked against the changed implementation.

Final follow-up verification: `python -m pytest -q -rs` passed **1,128 tests and
49 subtests**, with **79 skipped** optional integrations and the same nine fork
warnings. The 15 added freshness regression tests are included in that total.
The compiled Mojo protocol check and live watcher recovery/deletion check both
exited successfully on the final implementation. The earlier focused selection
passed 92 tests; a mistaken monkeypatch target in the new cache test was corrected
before that pass. No application behavior was weakened to make a check pass.
The 79 skips retain the optional-runtime limitations described above.
